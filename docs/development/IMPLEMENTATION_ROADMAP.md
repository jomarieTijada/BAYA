# Implementation Roadmap

## Purpose

This roadmap recommends an incremental order for the student to implement BAYA after the documentation-only foundation. Each stage has a checkpoint intended to keep architectural and thesis risks visible.

## Stages

| Stage | Objective | Prerequisites | Expected documentation | Expected future implementation outputs | Validation checkpoint |
|---|---|---|---|---|---|
| 1. Repository and documentation | Establish ownership, dependencies, terminology, traceability, security, and research boundaries | Approved thesis scope | Root overview, folder READMEs, dependency rules, decisions, roadmap | No application output; documentation baseline only | Every folder is explained and no framework or code is generated prematurely |
| 2. Shared domain terminology | Agree on characters, sounds, kudlit, strokes, attempts, mastery, feedback, rewards, and versions | Stage 1 | Glossary, module map updates, initial contract intent | Future framework-independent domain concepts | Stakeholders use consistent terms and ownership is unambiguous |
| 3. Mobile navigation shell | Prove learner journeys and feature entry points | Stages 1–2 and approved screen flow | Navigation map, accessibility notes, route ownership | Future route shell and screen placeholders created by the student | Onboarding, home, lessons, activities, handwriting, progress, achievements, profile, and settings are navigable without business rules in routes |
| 4. Local database foundation | Make local-first persistence a reliable base | Stages 1–3 and conceptual data model | Local data ownership, migration policy, retention, outbox design | Future SQLite adapters, local repositories, and migration history | Local writes survive restart; presentation cannot query the database directly |
| 5. Learning-content module | Deliver versioned characters, sounds, kudlit, syllables, words, and phrase lessons | Stages 2 and 4 | Content model, versioning, progression, acceptance criteria | Future learning domain, use cases, local repository, and lesson presentation | An offline learner can open approved content and record completion |
| 6. Quiz and assessment module | Support structured exercises, attempts, scoring, and summaries | Stages 2, 4, and 5 | Activity taxonomy, scoring rules, error cases, test plan | Future assessment domain, use cases, local persistence, and screens | Representative quiz types score consistently and persist results locally |
| 7. Canvas stroke collection | Capture ordered, reproducible handwriting input | Stages 3–4 and canvas interaction design | Stroke representation, input validation, accessibility, device assumptions | Future Skia presentation and canvas infrastructure adapter | Captured strokes preserve point order, stroke boundaries, timing, and canvas context |
| 8. ML data collection | Collect ethically governed Baybayin samples | Stages 2 and 7 plus ethics approval | Protocols, consent, annotations, quality control, dataset version policy | Future approved raw dataset versions and metadata | Raw data is immutable, consent constraints are recorded, and identities are separated |
| 9. Stroke preprocessing | Produce traceable comparable evaluator inputs | Stages 7–8 | Validation, normalization, smoothing, resampling, segmentation, kudlit separation, and version policy | Future reusable preprocessing research modules and tests | Transformations preserve stroke order and can be reproduced from a named raw version |
| 10. Comparative algorithm experiments | Compare DTW, multidimensional DTW, templates, baselines, and neural candidates fairly | Stages 8–9 | Hypotheses, configurations, splits, metrics, latency and compatibility protocol | Future experiment runs, result records, and evaluation reports | Each result names dataset, preprocessing, configuration, and evaluator versions |
| 11. Handwriting evaluator contract | Stabilize application-facing input and output semantics | Stages 2, 7, 9, and early Stage 10 findings | Evaluator contract, scoring dimensions, error taxonomy, version requirements | Future domain contract and application use case boundary | A controlled test double and at least two candidate adapters can express compatible results |
| 12. Selected algorithm integration | Integrate an approved evaluator without coupling business rules to it | Stages 10–11 and approval evidence | Manifest, compatibility, deployment, rollback, and fallback policy | Future local or server adapter, approved artifact, and version reporting | Results meet agreed feasibility thresholds and always record evaluator identity |
| 13. NLP validation | Add structured word and phrase checks | Stages 2, 5, and 6 | Scope, rules, error taxonomy, rule-set versioning, exclusions | Future deterministic NLP domain and application behavior | Supported cases return explainable classifications; translation and open chat remain excluded |
| 14. BAYA feedback orchestration | Convert structured results into controlled guidance | Stages 6, 11–13 | Feedback templates, error mapping, hint levels, repeated-error behavior | Future Feedback and BAYA Guide use cases and presentation | Same error and learning context produce reviewed, testable feedback without unrestricted generation |
| 15. Gamification | Award XP, levels, badges, achievements, and challenges safely | Stages 6 and 14 | Reward rules, stable award identity, duplicate-prevention scenarios | Future gamification domain, application workflows, and local storage | Replaying the same eligible operation never grants the reward twice |
| 16. Progress tracking | Consolidate lessons, scores, handwriting, activities, and mastery | Stages 5–6 and 12–15 | Mastery rules, summary definitions, data ownership, retention | Future progress use cases, local read models, and screens | Progress remains available offline and is derived from traceable outcomes |
| 17. Authentication | Connect learner identity without blocking the local-first foundation unnecessarily | Stages 3–4 and identity design | Token validation, authorization, session storage, recovery, privacy | Future Supabase Authentication adapter and identity workflows | Valid identity and ownership are checked separately; sensitive tokens are securely stored |
| 18. Backend synchronization | Reconcile local work with the modular-monolith backend | Stages 4, 15–17 and versioned contracts | Batch protocol, idempotency, conflicts, retries, acknowledgements, compatibility | Future outbox, API v1 synchronization, module handlers, and integration tests | Network interruption and repeated batches converge without lost work or duplicate rewards |
| 19. Analytics | Produce minimized operational and research-ready aggregates | Stages 16 and 18 plus privacy review | Metric definitions, event purpose, aggregation, retention, export review | Future analytics module and privacy-preserving exports | Statistics are traceable and do not expose unnecessary learner identity |
| 20. Testing and ISO 25010 evaluation | Build evidence for capabilities and selected quality characteristics | All applicable implementation stages | Testing strategy, instruments, acceptance criteria, ISO mapping, results | Future automated suites and thesis evaluation evidence | Findings distinguish designed support from measured outcomes and record limitations |
| 21. Release preparation | Prepare a reviewable mobile, API, content, and evaluator release | Stages 17–20 | Release checklist, compatibility matrix, migrations, monitoring, rollback, privacy review | Future release candidates and approved deployment artifacts | Versions are compatible, secrets are external, rollback is rehearsed, and required evidence is complete |

## Cross-Stage Rules

- Documentation and tests evolve with each implemented capability.
- Inner-layer behavior is established before framework-specific adapters.
- Local persistence precedes synchronization.
- The evaluator contract precedes final algorithm integration.
- An experiment result cannot promote an artifact without version, compatibility, and rollback metadata.
- Security, privacy, accessibility, and research ethics are stage gates rather than end-only activities.
- A stage is complete only when its validation checkpoint is evidenced, not merely when files exist.
