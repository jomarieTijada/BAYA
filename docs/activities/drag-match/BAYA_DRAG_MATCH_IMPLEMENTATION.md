# BAYA matching implementation

The normal Character Level checkpoint route renders MatchingChallenge for choice source records and the existing QuestionScreen for handwriting. No source JSON was rewritten. The old ChoiceOptions component remains for legacy regression coverage but is unreachable through the normal choice checkpoint route.

content/characterActivities/matching.ts derives 75 relationships from correctLetter, retains source identities and topic placements, rejects duplicate glyph classes/readings, and groups adjacent compatible records. Default boards have three pairs; a compatible trailing singleton can merge into a four-pair board. Unavoidable singleton groups preserve coverage without fabricated content. Two pending audio records have explicit unscored notice slides. The generated CSV lists all 100 source records.

MatchingChallenge owns provisional connections; connect enforces unique target ownership and supports undo. PanResponder and Animated.ValueXY provide native/web drag handling without dependencies. Tap and keyboard activation share connect. Target rectangles are measured on drag start. No correctness is revealed until transactional submission. Stable target ordering depends on attempt ID and board ID.

Existing audio controller provides mutually exclusive playback and local assets. Neutral Sound 1/2/3 controls never display the prompt. Audio must actually enter playing state before submission. Existing BayaMascot, StorySpeechBubble, SpeechBubbleTail, assessment header and completion dialog are reused.

No new package, migration table, model, image or audio asset was introduced. The service-worker asset manifest is regenerated by the production export. The export includes all existing learning assets.
